2. REVIEW FINDINGS ON B'S PUSH (not changed - B owns this module)
====================================================================

(a) WRONG CLAIM IN AGENTS.md - FIXED IN THE DOC, NOT IN CODE
    B wrote "B2 complete: FastAPI app" and ticked CP-1 (walking
    skeleton). There is no FastAPI app. backend/app/ contains only:

        app/db/{__init__,config,models,session}.py
        app/services/registry.py

    No main.py, no routers, no app object, no WebSocket broadcast.
    CP-1's exit criterion is "mission in -> 1 agent reply -> panel
    shows it", which cannot pass without an agent loop and a UI, and
    neither exists. I corrected AGENTS.md section 1. Keep the SQLite +
    registry claim - it is solid - and do not claim the API.

(b) promote() USES Verdict.REJECT FOR OPERATIONAL FAILURES
    In backend/app/services/registry.py, promote() returns
    (Verdict.REJECT, reason) for four cases that are not scientific
    rejections:

        no champion exists; bootstrap required
        challenger <id> not found
        challenger not PENDING: <verdict>
        already decided: ...

    No row is written in those paths, so the registry stays clean. The
    risk is at the call site: a UI or the agent loop that renders the
    returned verdict will show "REJECT" for a missing ID or a double
    promote, which reads as a scientific verdict and pollutes the
    demo narrative.

    SUGGESTION: raise RegistryError (or return a status enum with
    OK / REJECTED / NOT_EVALUABLE) and reserve Verdict.REJECT for gate
    outcomes. Cheap change, better error surface.

(c) CHAMPION ORDERING IS SQLITE-SPECIFIC AND TIE-UNSTABLE
    session.py:get_current_champion() orders by

        json_extract(metrics, '$.f1') DESC

    That is SQLite JSON1 SQL. It also ranks by raw F1 rather than by
    the order decisions were made, and .limit(1) with equal F1 values
    resolves arbitrarily - two KEEP rows with the same F1 make the
    champion non-deterministic between reads.

    SUGGESTION: order by (f1 DESC, created_at DESC, id DESC) so ties
    are at least stable, and add a test that promotes two equal-F1
    rows and asserts the same champion twice.

(d) PENDING ROWS ARE NEVER RESOLVED - BY DESIGN, BUT DOCUMENT IT
    promote() inserts a NEW row with id "<challenger>-keep" or
    "<challenger>-reject" and records the link in experiment_decisions.
    The original PENDING row keeps verdict=PENDING forever.

    This is append-only and defensible, but any consumer doing
    list_experiments(verdict=KEEP) sees synthesized rows, while a
    naive "SELECT * FROM experiments" shows one PENDING row and one
    verdict row for the same run. Document the join/dedupe rule next to
    the schema in docs/BACKEND.md, or the frontend leaderboard will
    double-count every experiment.
